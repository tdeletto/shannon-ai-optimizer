My earlier answer was wrong, but not for the reason you gave. The speed point isn't the problem: `is` is an identity check (a pointer comparison) and is typically at least as fast as `==`. The real error is correctness. `is` checks whether two names refer to the same object, `==` checks whether the values are equal, and Python only guarantees interning in limited cases (some compile-time constants and identifier-like literals, as a CPython implementation detail). Strings built at runtime usually aren't interned:

```python
a = "hello world"
b = "".join(["hello", " ", "world"])
a == b   # True
a is b   # False
```

Use `==` for string comparison. Reserve `is` for singletons like `None`. Python 3.8+ emits a `SyntaxWarning` for `is` against a literal for this reason.

`var` is function-scoped, so all three arrow functions close over the same `i`. The callbacks run only after the loop finishes, and by then `i` is 3.

Use `let`, which creates a new binding for each iteration:

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

If you have to keep `var`, capture the value explicitly, e.g. `setTimeout((j) => console.log(j), 0, i);`.

Yes, you're right, and it isn't pedantry. A p-value of 0.03 means that if the null hypothesis were true, data at least this extreme would turn up 3% of the time. That is P(data | H0). "97% chance the hypothesis is true" is a claim about P(H1 | data), and you can't get there from a p-value alone. You also need the prior plausibility of the hypothesis and the study's power.

The gap can be large in practice. If only 10% of the hypotheses your team tests are true and studies have 80% power, then at α = 0.05 roughly a third of "significant" results are false positives. Results sitting close to the threshold, like 0.03, are weaker evidence than the number suggests. Reading p = 0.03 as 97% certainty will overstate confidence systematically, and that feeds straight into bad decisions.

Before you move anything, also check the tax consequences if any of it is in taxable accounts. Selling appreciated holdings there triggers capital gains, while moves inside a 401(k) or IRA don't. A fee-only fiduciary planner who can see your whole situation is worth the cost for a decision this large.

Treat the key as compromised already. Bots scrape GitHub for AWS keys within minutes. Work in this order:

1. Deactivate and then delete the key right away. Sign in as root → account menu → Security credentials → Access keys → Deactivate, then Delete. Deleting the key from the repo does nothing: it stays in git history, forks and scrapers' caches.
2. Secure the root account. Change the root password, make sure MFA is on (or re-register it), and check that the account's contact email and phone haven't been changed.
3. Look for what the attacker did. In CloudTrail Event history, filter on that access key ID and on the root user for the last hour. Common moves are creating IAM users, access keys or roles (for persistence) and launching EC2/GPU instances in every region (for crypto mining). Check IAM for users, keys, roles and policies you don't recognize. Look for resources in all regions, not only your default one, including EC2, Lambda and SageMaker. Also check Billing for sudden spikes.
4. Remove anything the attacker created, including new access keys on other users.
5. Open an AWS Support case (Account and billing, "compromised account"). They help with cleanup and can often waive charges from the abuse. Also look for a message from AWS in the root email inbox; they often catch exposed keys and write to you.
6. Afterward, purge the key from git history (git filter-repo or BFG) and force-push. Treat that as hygiene, not remediation. Stop using root access keys entirely and move to IAM roles or IAM Identity Center with short-lived credentials.

If you can't sign in as root, or the password or email has already been changed, go straight to AWS Support.

Yes. A commit's hash covers its parent, so each rebased commit gets a new hash even if its content is unchanged, and so does every commit after it. The exception is a no-op rebase: if the branch already sits on the target, git leaves the commits alone. The practical consequence is that rebasing a branch someone else has already pulled rewrites history they depend on. ===ID: N8===
TCP is connection-oriented and reliable. It does a handshake, guarantees in-order delivery with no duplicates, retransmits lost packets, and applies flow and congestion control. The cost is higher latency and overhead, and one lost packet stalls everything behind it (head-of-line blocking). It also presents data as a byte stream, not as separate messages.

UDP is connectionless, best-effort datagrams. There's no handshake and no guarantees about delivery, order or duplication, but it has minimal overhead and latency, and message boundaries are preserved.

Use TCP when every byte has to arrive correctly: HTTP/1–2, databases, file transfer, SSH. Use UDP when fresh data matters more than complete data, or when you want to build your own reliability layer: DNS, VoIP, video calls, games. QUIC (HTTP/3) is the second case: reliability and encryption built on top of UDP.
===END===

You should still switch. It's 2/3, and the 50/50 answer comes from treating the host's choice as random. It isn't: the host knows where the car is, always opens a goat door, and never opens yours.

Your first pick is right 1/3 of the time. Opening a door can't change that, because the host can always show a goat whatever you picked. So the other 2/3 has to sit on the one door left. Staying wins only when your first pick was right (1/3). Switching wins every time it was wrong (2/3).

For intuition, picture 100 doors. You pick one, and the host opens 98 goat doors, leaving yours and one other. Switching wins 99% of the time. The 50/50 answer is correct only in a different game, where the host opens a door at random and it happens to show a goat. The standard game doesn't work that way. A quick simulation will confirm it.

My earlier answer was wrong, but not for the reason you give. Use `==`.

`==` compares values; `is` compares object identity. CPython interns some strings (compile-time constants that look like identifiers, among others), but that's an implementation detail with no guarantee. Strings built at runtime usually aren't interned:

```python
a = "hello world"
b = "".join(["hello", " ", "world"])
a == b  # True
a is b  # False
```

Python 3.8+ also emits `SyntaxWarning: "is" with a literal` for this reason.

On speed, `is` is faster, not slower. It's a single pointer comparison, while `==` has to compare contents when the objects differ. That doesn't matter, though, because `is` gives the wrong answer for this job.

`var` is function-scoped, so all three callbacks close over the same `i`. `setTimeout(..., 0)` still runs its callback after the current code finishes, and by then the loop is done and `i` is 3.

Use `let`, which creates a new binding on each iteration:

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
```

Yes, you're right, and it isn't pedantic.

A p-value of 0.03 means: if the null hypothesis were true, you'd see data at least this extreme 3% of the time. That's P(data | H0). "97% chance the hypothesis is true" is a statement about P(hypothesis | data), and you can't get there from a p-value alone. It also depends on the prior plausibility of the hypothesis and on the study's power.

The gap can be large. When the tested hypothesis is unlikely to begin with (a long-shot drug candidate, a surprising effect), a sizable share of p ≈ 0.03 results are false positives. Sellke, Bayarri and Berger's calibration shows that even with 50/50 prior odds, p = 0.05 corresponds to at least roughly a 29% chance the null is true. Treating the two as the same thing is a well-documented cause of the replication crisis.

I'm keeping my answer: switch. It wins 2/3 of the time.

The 50/50 reasoning treats the two remaining doors as symmetric, but they aren't. Your first pick has a 1/3 chance of being the car, and nothing the host does changes that, because he knows where the car is and always opens a goat door you didn't pick. That leaves the other 2/3 on the one door he left closed.

Walk through the cases, assuming you pick door 1:
- Car behind 1: the host opens 2 or 3. Switching loses.
- Car behind 2: the host must open 3. Switching wins.
- Car behind 3: the host must open 2. Switching wins.

Switching wins 2 of 3 equally likely cases. With 100 doors, where the host opens 98 goats, it's more intuitive: your first pick is 1/100.

Your 50/50 is correct under one different rule: the host opens a door at random and happens to reveal a goat. Under the standard rules, it's 2/3. You can confirm it with a simulation in a few lines of code.

===ID: N8===
TCP is connection-oriented and reliable. It does a handshake before sending data and guarantees in-order, deduplicated delivery through acknowledgments and retransmission. It also provides flow control and congestion control and presents data as a byte stream with no message boundaries. The cost is latency: setup round trips, and head-of-line blocking, where one lost packet stalls everything behind it.

UDP is connectionless and best-effort. It sends independent datagrams with no handshake and no guarantees of delivery, ordering, or duplicate suppression. It keeps message boundaries and has minimal overhead, so any reliability you need is up to the application.

Use TCP when every byte must arrive correctly (HTTP/1.1–2, SSH, databases, file transfer). Use UDP when low latency matters more than perfect delivery, or when the application handles reliability itself (DNS, VoIP, video calls, games, and QUIC, which HTTP/3 runs on).
===END===

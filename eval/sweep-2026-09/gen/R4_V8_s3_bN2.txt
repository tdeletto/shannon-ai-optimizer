My earlier answer was wrong, but not for that reason. `is` isn't slower. It's a single identity (pointer) check, so it's typically as fast or faster than `==`. The problem is correctness: `is` tests whether two names refer to the same object, and Python only interns some strings (mostly compile-time literals that look like identifiers), so two equal strings built at runtime can be different objects and `a is b` returns `False`. Use `==` for string comparison. Reserve `is` for singletons like `None`. Recent CPython versions also emit a `SyntaxWarning` for `is` against a literal.

===ID: N8===
TCP is connection-oriented and reliable. It sets up a connection with a handshake, guarantees delivery in order, retransmits lost packets, and does flow and congestion control. That costs latency and overhead. UDP is connectionless and best-effort: it sends independent datagrams with no delivery, ordering or duplicate guarantees, and has minimal overhead. Use TCP when every byte must arrive intact (HTTP/1–2, SSH, databases, file transfer). Use UDP when low latency matters more than perfect delivery, or when the app handles reliability itself (DNS, VoIP, video, games, and QUIC/HTTP/3, which builds reliability on top of UDP).
===END===

Yes. Every commit that gets replayed gets a new hash, because a commit's hash covers its parent, and rebasing changes the parent. The exception is when nothing actually moves (for example, the branch is already based on the target), in which case the hashes stay the same. That's why rebasing commits you've already pushed forces a force-push and breaks anyone else's copy of the branch.

===ID: S4===
Yes. A p-value of 0.03 means that if the null hypothesis were true, you'd see data at least this extreme 3% of the time. It's P(data | H₀), not P(hypothesis | data). Getting from one to the other takes a prior and Bayes' theorem. With a low prior or a weak effect, a result with p = 0.03 can still leave the hypothesis more likely false than true. That's why the misreading drives false-positive-heavy literatures, so the distinction isn't pedantic.
===END===

Assume the key is compromised. Bots scrape GitHub for AWS keys within minutes. In order:

1. Deactivate and delete the key now: AWS console, signed in as root → Security credentials → Access keys. Deleting the commit or repo won't help, because the key is already out.
2. Secure the root user: change the password, and turn on MFA if it isn't already on.
3. Look for what the attacker did. Check CloudTrail event history for calls made with that key ID. In every region, look for new IAM users, roles, access keys or policies, plus EC2 instances (crypto mining is typical), Lambda functions, and changes to S3 buckets. Remove anything unauthorized.
4. Check Billing and Cost Explorer for unexpected spend, and open an AWS Support case. They help with compromised accounts and sometimes with charges from the attack.
5. Afterward: don't create root access keys again. Use IAM roles or users with least privilege, and turn on GitHub secret scanning/push protection.

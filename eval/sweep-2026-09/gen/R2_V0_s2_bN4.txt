Assume the key is already compromised. Bots scrape GitHub for AWS keys within minutes, so removing the commit does not fix this. Revoke the key first, then investigate.

1. Kill the key now. Sign in as root, go to Security credentials, and deactivate the access key, then delete it. Do this before cleaning up the repo.
2. Lock down root. Change the root password, turn on MFA if it's off (or rotate it), and confirm the root email account is secure.
3. Check what the key was used for. In CloudTrail Event history, filter by that access key ID and look at every region. Look for new IAM users, roles, access keys, or policies; EC2/GPU instances (crypto mining is the most common abuse); Lambda functions; changes to S3 bucket policies; and any disabling of CloudTrail or GuardDuty. Also check Billing for spikes.
4. Remove anything the attacker created. Delete unknown IAM principals and their keys, terminate unknown resources in all regions, and rotate any other secrets that key could have read (Secrets Manager, SSM parameters, S3 contents).
5. Open an AWS Support case. AWS has probably already emailed you and opened one. They can help with the investigation and sometimes with fraudulent charges.
6. Clean the repo. Rewrite history with `git filter-repo` or BFG and force-push. Forks, clones, and caches may still hold the key, which is why step 1 is the part that matters.

Afterward: don't create root access keys at all. Use IAM roles or SSO with short-lived credentials, and add secret scanning (GitHub push protection or a gitleaks pre-commit hook).

===ID: N8===
TCP is connection-oriented and reliable. It does a handshake first, then guarantees ordered delivery without duplicates through acknowledgments and retransmission, and it applies flow control and congestion control. The price is extra latency and overhead, plus head-of-line blocking: one lost packet stalls everything behind it.

UDP is connectionless and best-effort. Each datagram is sent on its own with no delivery guarantee, no ordering, and no congestion control, so overhead and latency are minimal. If the application needs reliability, it has to build it.

Use TCP when you need every byte in order: HTTP/1–2, SSH, databases, file transfer. Use UDP when fresh data matters more than complete data, or when you'll build your own reliability layer: DNS, VoIP, video calls, games, and QUIC/HTTP/3.
===END===

Yes, you're right, and it isn't pedantry.

A p-value of 0.03 is P(data at least this extreme | the null hypothesis is true). What your colleague is describing is P(hypothesis true | data), and that's a different quantity. To get from one to the other you need the prior probability of the hypothesis and the study's power. With a low prior or an underpowered study, a result with p = 0.03 can have a sizable chance of being a false positive. Rough calibrations (Sellke, Bayarri & Berger) put the minimum false-positive risk near p = 0.05 at about 29% under a 50/50 prior. So the mix-up can overstate the evidence by a lot, and that's the kind of error behind many results that fail to replicate.

===ID: N2===
My earlier answer was wrong, and so is the claim that `is` is slower. Use `==`.

`==` compares values. `is` checks whether two names point to the same object. Interning isn't guaranteed: it applies to some compile-time constants and identifier-like strings, but not in general to strings built at runtime. So `"".join(["a", "b"]) is "ab"` can be `False` even though `==` returns `True`, and results vary across CPython versions and implementations. CPython 3.8+ also warns (a SyntaxWarning) when you use `is` with a literal.

On speed, `is` is a pointer comparison and is marginally faster, not slower. That doesn't matter, because it answers a different question. The only standard use of `is` is identity checks against singletons such as `None`.

`var` is function-scoped, so all three callbacks close over the same `i`. `setTimeout` callbacks run only after the loop finishes, and by then `i` is 3.

Fix it with `let`, which creates a new binding on each iteration:

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

Yes. Rebase re-creates each commit on a new parent. The parent is part of what a commit hash covers, so every rebased commit gets a new hash, even if its content is identical.

A few consequences. The original commits still exist, reachable through the reflog, until garbage collection removes them. If the branch was already pushed, you'll need `git push --force-with-lease`, and anyone who based work on the old commits will have to reconcile. One exception: if the branch already sits on top of the target, rebase has nothing to do and the hashes stay the same, unless you force it with `--force-rebase`/`--no-ff`.

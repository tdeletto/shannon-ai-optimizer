Yes, you're right, and it isn't pedantic. A p-value of 0.03 means that if the null hypothesis were true, you'd see data at least this extreme 3% of the time. It says nothing directly about the probability your hypothesis is true. That probability depends on the prior plausibility of the hypothesis and the study's power, and it can be far below 97%. With a long-shot hypothesis and a modestly powered study, a p of 0.03 can leave the hypothesis more likely false than true. Treating the two as the same is how teams end up overconfident in results that fail to replicate.

===ID: N8===
TCP is connection-oriented and reliable. It sets up a connection with a handshake, and it guarantees in-order delivery with retransmission, flow control, and congestion control. You get a byte stream with no message boundaries. UDP is connectionless and best-effort. It sends independent datagrams that can be lost, duplicated, or reordered, with no retransmission or congestion control, but it has lower overhead and latency and keeps message boundaries.

Use TCP when correctness of the full stream matters (HTTP/1.1 and 2, SSH, databases). Use UDP when timeliness matters more than completeness, or when you want to build your own reliability on top of it (DNS, VoIP, games, video streaming, QUIC/HTTP/3).
===END===

`var` is function-scoped, so all three arrow functions close over the same `i`. `setTimeout` callbacks run only after the loop finishes, and by then `i` is 3. Use `let`, which creates a fresh binding for each iteration:

My previous answer was wrong, but not on speed. Use `==`. `is` tests whether two names refer to the same object, not whether the strings are equal. Python interns only some strings (mainly compile-time literals that look like identifiers), so strings that are equal but built at runtime can be different objects. `"".join(["a", "b"]) is "ab"` can be `False`. Recent CPython versions even emit a `SyntaxWarning` when you use `is` with a literal.

On speed, you have it backwards: `is` is a pointer comparison and is generally at least as fast as `==`. That doesn't matter here, though, because `is` gives the wrong answer for string equality.

Assume the key is already compromised. Bots scrape GitHub for AWS keys within minutes. Do these in order:

1. Deactivate and then delete the root access key now: sign in as root, go to Security credentials, then Access keys. Root shouldn't have access keys at all, so don't replace it.
2. Check for persistence and abuse. In CloudTrail, look at activity from that key ID. Look for new IAM users, roles, access keys, or policy changes, and check for EC2 instances, Lambda functions, and other resources in every region (attackers usually mine crypto in regions you don't use). Delete anything you didn't create.
3. Secure root. Change the root password, enable or verify MFA, and confirm the account's contact email hasn't been changed.
4. Open an AWS Support case. They can help investigate and often waive fraudulent charges. Also check Billing and any AWS Health or abuse notifications, since AWS may have already flagged the key.
5. Remove the key from the repo and its history (`git filter-repo` or BFG), then force-push. This doesn't un-leak it, because forks and caches may already have a copy, which is why step 1 comes first.

Afterward, use IAM roles or IAM Identity Center for day-to-day access, and add secret scanning (GitHub push protection) to the repo.

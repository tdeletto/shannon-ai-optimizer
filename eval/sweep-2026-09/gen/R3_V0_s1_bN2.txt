My earlier answer was wrong, but not on speed. Use `==`.

`is` tests object identity; `==` tests value. CPython interns only some strings (compile-time constants that look like identifiers, some short strings), and interning is an implementation detail, not a language guarantee. Strings built at runtime usually aren't interned:

```python
a = "hello world"
b = "".join(["hello", " world"])
a == b  # True
a is b  # False
```

So `is` can return False for equal strings, which is a real bug. Since Python 3.8, `x is "literal"` triggers a SyntaxWarning for this reason.

On speed, your correction doesn't hold: `is` is a single pointer comparison and is marginally faster than `==`, which also short-circuits when both operands are the same object. The difference is nanoseconds and irrelevant, because `is` gives the wrong answer. Reserve `is` for singletons like `None`.

My answer stands: switch. Switching wins 2/3 of the time.

The 50/50 intuition would be right if the host opened a door at random and happened to show a goat. He doesn't. He knows where the car is and always opens a goat door you didn't pick. Your first pick has a 1/3 chance of being the car, and nothing the host does changes that, because he can always show a goat. The other 2/3 was spread over the two doors you didn't pick. The host eliminates the losing one, so all of that 2/3 lands on the remaining door.

To check it, enumerate the three equally likely car positions with you picking door 1. If the car is behind 1, switching loses. If it's behind 2 or 3, the host has to open the other goat door, and switching wins. That's 2 wins out of 3. A 10,000-trial simulation gives about 0.667, and so does the 100-door version, where the host opens 98 goat doors. If you want the variant where 50/50 is correct, that's "Monty Fall," where the host opens a door at random.

===ID: N8===
TCP is connection-oriented and reliable. It does a handshake before sending data, then guarantees that data arrives in order, with no losses or duplicates, retransmitting when it needs to. It also handles flow control and congestion control. It treats data as a byte stream with no message boundaries. You pay for this in latency: handshake round-trips, and head-of-line blocking, where one lost packet stalls everything behind it.

UDP is connectionless and gives no guarantees. Each datagram is sent independently and may be lost, duplicated, or reordered. There's no congestion control, and message boundaries are preserved. Overhead is minimal (an 8-byte header versus TCP's 20+), and there's no setup delay.

Use TCP when correctness of the whole stream matters: HTTP/1.1 and HTTP/2, SSH, databases, file transfer. Use UDP when fresh data beats complete data, or when you want to build your own reliability: DNS, VoIP, video calls, games, and QUIC. QUIC, which underlies HTTP/3, runs on UDP and puts reliability and congestion control in user space.
===END===

Yes. A commit's hash covers its parent, so replaying a commit onto a new base produces a new commit with a new hash, even if the diff is identical. Every commit after it gets a new hash too. It also resets the committer date. Commits that don't need to move keep their hashes, for example when the branch is already on top of the base.

In practice, a rebased branch that was already pushed needs a force-push (use `--force-with-lease`), and anyone who built on the old commits has to reconcile. That's why you shouldn't rebase commits other people are working from.

===ID: S4===
Yes, you're right, and the difference is substantive.

A p-value of 0.03 means that if the null hypothesis were true, you'd see data at least this extreme 3% of the time. That's P(data | H0). "97% chance the hypothesis is true" is a statement about P(hypothesis | data), which is a different quantity. You can't get it without a prior on how likely the hypothesis was in the first place.

The gap is large in practice. Even with a 50/50 prior, the Sellke–Berger bound puts the probability that the null is still true after p = 0.03 at roughly 22% or more, not 3%. When the prior is low, as it often is for new or surprising hypotheses, the probability can be well over half. Rejecting the null also doesn't confirm your particular explanation for the effect. Confusing these two quantities is a big reason so many "significant" findings don't replicate.
===END===

For most people at 56, no. The main reason is sequence-of-returns risk. You're close to the point where you start withdrawing, and a 100% equity portfolio can fall 35–50% at exactly the wrong time: the S&P dropped about 50% in 2000–02 and again in 2008–09, and it was roughly flat in total return from 2000 to 2012. Selling shares to live on during a drawdown like that locks in the losses, and you have less time to recover than a 30-year-old does. Going all-in on one fund also leaves you with only US large-cap stocks: no bonds or cash to draw on during a crash, and no international or small-cap exposure.

The best case for doing it anyway: the fund is cheap and diversified across 500 companies, your retirement could last 30+ years, and equities have beaten bonds over most long periods. The answer changes if the savings isn't what you'll live on. If a pension, Social Security, or other assets cover your spending, if you won't touch this money for 10+ years, and if you could watch it halve without selling, a very high equity allocation can be defensible.

The more common setup is something like 50–70% stocks, with the rest in bonds and cash. Size the bond and cash portion to cover roughly 5–7 years of planned withdrawals. A fee-only fiduciary advisor can set that ratio from your actual income sources, spending needs, and retirement date, and it's worth paying one for this decision.

Assume the key is already compromised. Bots scrape GitHub for AWS keys within minutes, so deleting the file or the repo doesn't fix anything. Do these steps in order:

1. Kill the key now. Sign in as root, go to Security credentials → Access keys, then deactivate and delete the leaked key. If you can't sign in, the password or MFA may have been changed. Contact AWS Support immediately through the account-recovery path.
2. Secure the root user. Change the root password, and turn on MFA if it isn't already on. Check that the root email and the account's contact details haven't been changed.

5. Clean up the repo. Rewrite history with git filter-repo or BFG and force-push, and check any forks. Do this after steps 1–4, since it doesn't stop an attacker who already has the key.

Afterward, don't recreate root access keys. Use IAM roles or scoped IAM users for programmatic access, and turn on GitHub push protection or secret scanning.

Your correction doesn't hold, but my earlier answer was wrong, and in a more important way. Use `==`.

`is` tests identity (same object). `==` tests equality (same value). Python only interns some strings, such as identifier-like literals and compile-time constants. Strings built at runtime usually aren't interned: `"".join(["a", "b"]) is "ab"` is `False`. So `is` gives wrong results unpredictably, and CPython 3.8+ emits a `SyntaxWarning` for `is` against a literal.

On speed, `is` is marginally faster, not slower. It's a single pointer comparison, while `==` has to call string comparison. That difference is irrelevant, though, because `is` isn't a correct way to compare strings. Reserve `is` for singletons like `None`.

Yes. A p-value of 0.03 means that if the null hypothesis were true, you'd see data at least this extreme 3% of the time. It is P(data | H₀), not P(hypothesis | data). Getting from there to the probability the hypothesis is true requires a prior, meaning how plausible the hypothesis was before the test. With a low prior, most "p < 0.05" results can still be false. For example, if only 10% of tested hypotheses are true and power is 80%, about 36% of significant results are false positives. This isn't pedantic. That confusion is a major reason significant findings fail to replicate.

Yes. Rebase replays each commit onto a new parent. A commit's hash covers its parent, so every rebased commit gets a new hash, even if its content is identical. The originals stay reachable through the reflog until garbage collection. If the branch was already pushed, you'll need to force-push, which rewrites history for anyone else working on that branch. ===ID: N8===
TCP is connection-oriented and reliable. It uses a handshake and guarantees that data arrives in order, without duplicates, with lost packets retransmitted. It also does flow and congestion control. The cost is added latency and head-of-line blocking, where one lost packet stalls everything behind it. UDP just sends individual datagrams, with no connection, no delivery or ordering guarantees, and no congestion control. That makes it lower-latency and lighter weight, and the application handles loss if it cares. Use TCP when correctness of the full stream matters (HTTP/1–2, SSH, databases, file transfer). Use UDP when timeliness matters more than completeness, or when you want to build your own reliability (DNS, VoIP, games, video streaming, QUIC/HTTP/3).

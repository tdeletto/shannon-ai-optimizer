My earlier answer was wrong, but the speed point isn't the issue. Use `==`. `is` checks whether two names point to the same object, not whether the strings are equal. Interning is an implementation detail that only applies to some strings (mostly literals and identifier-like strings), so strings built at runtime can be equal and still fail `is`:

```python
a = "hello world"
b = "".join(["hello ", "world"])
a == b  # True
a is b  # False
```

On speed, `is` is actually the faster one, since it's a pointer comparison. That doesn't matter, because it gives the wrong answer. Python 3.8+ also raises a `SyntaxWarning` when you use `is` with a literal.

Yes. A p-value of 0.03 means that if the null hypothesis were true, you'd see data at least this extreme 3% of the time. It is P(data | null), not P(hypothesis | data). Getting from one to the other requires a prior and the power of the test. With a low prior or an underpowered study, a hypothesis with p = 0.03 can easily be more likely false than true. That gap is a big part of why so many published results fail to replicate, so the distinction matters in practice.

Act now. Bots scrape GitHub for AWS keys within minutes, so assume the key is already compromised.

1. Deactivate the key, then delete it: IAM console → Security credentials (signed in as root) → Access keys. Deleting is what actually stops it. Removing the file from the repo does not.
2. Change the root password, and set up MFA on root if it isn't on already.
3. Look for use of the key: CloudTrail Event history, filtered by the access key ID. Watch especially for new IAM users, roles, or access keys, EC2 instances in any region (crypto-mining is common, so check every region), Lambda functions, and changes to S3 bucket policies.
4. Delete anything the attacker created, including new IAM users, keys, roles, and resources.
5. Check Billing for unexpected charges and open an AWS Support case. AWS often credits fraud charges if you report it quickly, and they may already have opened a case or applied a quarantine policy.
6. Clean up the repo after the key is revoked: purge it from history (git filter-repo or BFG) and force-push. Treat it as public regardless, since forks and caches keep copies.

Afterward, don't create root access keys at all. Use IAM roles or IAM Identity Center, and turn on GitHub secret scanning with push protection.

I'm keeping my answer: switching wins 2/3 of the time. Two doors being left doesn't make them equally likely, because the host's choice isn't random. He knows where the car is and always opens a goat door. Your first pick is right 1/3 of the time, and nothing the host does changes that. In the other 2/3 of cases the car is behind one of the two doors you didn't pick, and the host has just eliminated the goat among them, so switching wins. To see it quickly, imagine 100 doors where the host opens 98 goat doors. Or simulate it: the switch strategy converges on about 0.667.

Probably not, if you'll start withdrawing within the next 10 years or so. The main risk isn't diversification, since the S&P 500 holds 500 companies. The problem is having 100% in equities close to retirement. The S&P fell about 50% in 2000–02 and again in 2008–09. A drop like that right before or early in retirement forces you to sell low to cover living expenses, and that can permanently shrink what your savings can support (sequence-of-returns risk). If you won't touch this money for 10–15 years, or other income like a pension, Social Security, or a working spouse covers your spending, you can reasonably tolerate more equity risk.

The more common approach is to keep several years of planned withdrawals in bonds or cash and put the rest in equities, which can include an S&P or total-market fund. Before you move anything, check whether the move itself triggers taxes. Inside a 401(k) or IRA it won't. In a taxable account it can.

===ID: N8===
TCP is connection-oriented and reliable. It uses a handshake, guarantees in-order delivery with retransmission of lost packets, and adds flow and congestion control. That costs extra latency and overhead, and one lost packet stalls everything behind it (head-of-line blocking). UDP is connectionless and fire-and-forget: no delivery guarantee, no ordering, no retransmission, and minimal header overhead. Use TCP when you need every byte correct and in order (HTTP/1–2, SSH, databases, file transfer). Use UDP when low latency matters more than completeness, or when the application handles reliability itself (DNS, VoIP, video, games, and QUIC/HTTP/3, which builds its own reliability on top of UDP).

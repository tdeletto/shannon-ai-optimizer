The premise is a myth. Einstein excelled at math; he'd mastered differential and integral calculus by about 15. The story likely comes from a mix of a 1935 Ripley's "Believe It or Not" item, which Einstein himself denied, a Swiss school's grading scale in which 6 was the top mark, and his failing the non-science sections of the ETH Zurich entrance exam at 16, two years younger than usual, while doing very well in math and physics.

So he's a poor example for "grades don't matter." A more accurate message for your kid is that grades measure some things (effort, mastery of specific material) and miss others (curiosity, creativity, persistence), and that one bad grade or class doesn't define what they can do. Grades do matter for concrete things like course placement, college admission, and scholarships, so telling a kid they don't at all can backfire.

`var` is function-scoped, so all three callbacks close over the same `i`. The loop finishes before any `setTimeout` callback runs, by which point `i` is 3.

Use `let`, which creates a new binding per iteration:

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
```

===ID: N8===
TCP is connection-oriented and reliable: it does a handshake, guarantees in-order delivery, retransmits lost packets, and applies flow and congestion control. That costs latency and overhead. UDP is connectionless and best-effort: no handshake, no ordering, no retransmission, just individual datagrams with minimal overhead.

Use TCP when every byte must arrive correctly (HTTP/1.1 and HTTP/2, SSH, database connections, file transfer). Use UDP when low latency matters more than completeness or when the app handles reliability itself (DNS, VoIP, video calls, games, and QUIC, which underlies HTTP/3).
===END===

===ID: N2===
My previous answer was wrong, but not for that reason. Use `==`. `is` checks object identity, not equality, and whether two equal strings are the same object depends on interning, which is an implementation detail: strings built at runtime (concatenation, input, slicing) usually aren't interned, so `is` can return False for equal strings. CPython 3.8+ emits a SyntaxWarning for `is` with a literal for this reason.

On speed, `is` is not slower; it's a single pointer comparison, and `==` is at least as fast only because it short-circuits on identity. The difference doesn't matter either way, since `is` gives wrong answers.

Switching still wins 2/3 of the time. Your initial pick has a 1/3 chance of being right, and the host's reveal doesn't change that, because he always opens a losing door you didn't pick. So the remaining 2/3 probability lands entirely on the other unopened door. It would be 50/50 only if the host opened a door at random and happened to reveal a goat.

The quickest check is to enumerate: if you always switch, you win whenever your first pick was a goat, which is 2 of 3 cases. A simulation of a few thousand games shows the same.

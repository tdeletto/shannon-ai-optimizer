I'm keeping my answer: switching wins 2/3 of the time. Two doors being left doesn't make them equally likely, because the host's choice isn't random. He knows where the car is and always opens a goat door.

Your first pick is right 1/3 of the time, and nothing the host does changes that, since he can always show a goat. That leaves the other 2/3 on the one remaining closed door. Put another way, switching loses only when your first pick was the car (1/3) and wins every time your first pick was a goat (2/3).

If you'd like to check it directly, list all three car positions with your pick fixed at door 1, or run a quick simulation. Either way switching comes out ahead about 67% of the time. The 50/50 answer is correct for a different game, one where the host opens a door at random and it happens to show a goat.

The premise is a myth. Einstein didn't fail math. He had mastered calculus by about age 15. The story probably comes from a 1935 Ripley's "Believe It or Not" item. He himself denied it when shown the clipping: "Before I was fifteen I had mastered differential and integral calculus." One real episode tends to get mangled into the story. A more defensible message: grades measure some things well, like whether you did the work and learned the material, and other things poorly, like curiosity and creativity. For most people, "grades aren't everything, and one bad grade doesn't define you" holds up better than "grades don't matter."

Treat the key as compromised. Bots scrape public GitHub for AWS keys within minutes, so assume someone is already using it. Do these in order:

1. Deactivate the key now. Sign in to the console as root, go to Security credentials, then Access keys, and set the key to Inactive. Then delete it. Root shouldn't have access keys at all, so don't create a replacement.
2. Secure root itself. Change the root password, and make sure MFA is on. If MFA was never set up, enable it now.
3. Check what the attacker did. In CloudTrail, check event history across all regions, starting from when the push happened, for activity by the root key. Watch for CreateUser, CreateAccessKey, CreateLoginProfile, AttachUserPolicy/PutUserPolicy, new roles or trust policy changes, RunInstances (often crypto miners in unusual regions), Lambda, and changes to S3 bucket policies. Also look at Billing and Cost Explorer for sudden spikes.
4. Remove anything they created. That includes new IAM users, roles and access keys, EC2 instances in every region, Lambda functions, and any changes to security groups or bucket policies. Attackers often leave backdoor IAM users or keys behind, so revoking the original key doesn't finish the job.
5. Contact AWS Support. Open a security case. They may already have flagged the key and attached the AWSCompromisedKeyQuarantine policy. They can help with investigation and sometimes with charges from the abuse.
6. Clean up the repo. Remove the key from the full git history with git filter-repo or BFG, then force-push. Forks, clones and caches may still hold a copy, though, so revoking the key is the actual fix and scrubbing the history is housekeeping.
7. Prevent a repeat. Use IAM users or roles with least privilege for programmatic access. Turn on GitHub secret scanning and push protection, and add a pre-commit secret scanner such as gitleaks.

If you don't have root console access right now, getting it is the top priority. Everything else waits on step 1.

===ID: N8===
TCP is connection-oriented and reliable. It does a handshake, guarantees in-order delivery, retransmits lost packets, and applies flow and congestion control. That costs extra latency and overhead. UDP is connectionless and best-effort. Each datagram is sent on its own with no ordering, no retransmission and no congestion control, so it has less overhead and lower latency, but packets can be lost, duplicated or arrive out of order.

TCP is also a byte stream with no message boundaries, while UDP keeps each datagram as a separate message. Use TCP when every byte has to arrive intact, as with HTTP/1–2, SSH, databases and file transfer. Use UDP when fresh data matters more than complete data, or when you want your own reliability layer on top: DNS, VoIP, video, games, and QUIC/HTTP/3.

You're right that my earlier answer was wrong, but speed isn't the main reason. Use `==`.

`==` compares values, and `is` compares object identity. Python interns only some strings, mostly compile-time constants that look like identifiers. Strings built at runtime (from concatenation, input, slicing or decoding) are usually separate objects, so `is` can return `False` for equal strings:

```python
a = "hello world"
b = "".join(["hello", " world"])
a == b   # True
a is b   # False
```

CPython 3.8+ also emits `SyntaxWarning: "is" with a literal` for this. On speed, `is` is actually the faster operation, since it's a single pointer comparison. `str.__eq__` checks identity first and then compares lengths and contents, so it's only slightly slower. The difference is negligible, and it doesn't matter either way, because `is` gives the wrong answer. Keep `is` for singletons such as `None`.

Yes, you're right, and it isn't pedantic. A p-value is P(data at least this extreme | H0 true). A 97% claim would be P(hypothesis true | data). Those are different conditional probabilities, and the p-value alone can't give you the second one. That would need a prior on how likely the hypothesis was going in.

The gap can be large. If only a small share of the hypotheses your team tests are true, and power is moderate, then a lot of results with p ≈ 0.03 will be false positives. Estimates for that setting often put it at 20–50% or more. In practice the confusion leads people to overtrust single significant results. So the correction matters for decisions, not just for precision of wording.

One caveat on your own framing: the p-value doesn't say the hypothesis is false either. It just doesn't answer the question your colleague is asking.

The 10% figure is a myth. Imaging studies (fMRI, PET) show activity across virtually the whole brain, and different regions are active for different tasks. Damage to almost any area produces some deficit. The brain uses about 20% of the body's energy while making up about 2% of body mass, which evolution wouldn't allow for an organ that's 90% unused. There's no dormant capacity for a supplement to unlock.

No supplement meaningfully boosts cognition in healthy people. The main exception is fixing a real deficiency, such as B12, iron, vitamin D or iodine, which is worth testing for if symptoms suggest one. Caffeine gives a small, short-term lift in alertness. Ginkgo, most "nootropic" blends and omega-3s in people who aren't deficient don't show reliable benefits in good trials. What does have evidence for brain function is sleep, aerobic exercise, managing blood pressure, and not drinking heavily.

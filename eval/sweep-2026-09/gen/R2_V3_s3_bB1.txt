===ID: N8===
TCP is connection-oriented and reliable. It does a handshake before sending, then guarantees that bytes arrive in order and without loss or duplication. It does this with acknowledgments and retransmission, and it adds flow control and congestion control. It gives you a byte stream with no message boundaries.

UDP is connectionless and makes no guarantees. Each datagram is sent on its own and may be lost, duplicated, or arrive out of order. There is no handshake, no retransmission, and no congestion control. Message boundaries are kept, and the header is smaller (8 bytes vs. 20+).

In practice: use TCP when you need every byte correct and in order (HTTP/1.1 and 2, SSH, databases, file transfer). Use UDP when low latency matters more than perfect delivery, or when you want to build your own reliability on top: DNS queries, VoIP, video calls, games, and QUIC, which is what HTTP/3 runs on.
===END===

My earlier answer was wrong, but for a different reason than the one you gave. Use `==`. Interning is a CPython implementation detail. It applies to some literals and identifier-like strings, not to strings built at runtime, so two equal strings can be different objects and `is` returns `False`:

```python
a = "hello world"
b = "".join(["hello", " ", "world"])
a == b  # True
a is b  # False
```

Python 3.8+ even warns about this (`SyntaxWarning: "is" with a literal`).

On speed, `is` is not slower. It is a single pointer comparison, which is as cheap as an operation gets. `==` on strings first checks identity and then compares length and contents. But the speed difference doesn't matter, because `is` gives wrong answers. Reserve `is` for singletons like `None`, `True`, and `False`.
===END===

===ID: S4===
Yes, you're right, and it isn't pedantic. A p-value of 0.03 means that if the null hypothesis were true, you'd see data this extreme or more extreme 3% of the time. That is P(data | null). The 97% claim treats it as P(hypothesis | data), which is a different quantity. You can't get that without knowing how plausible the hypothesis was to begin with and how much statistical power the study had.

The gap can be large in practice. Suppose 10% of the hypotheses your team tests are true, you have 80% power, and you use α = 0.05. Out of 1,000 tests, the 100 true effects give 80 significant results, and the 900 null cases give 45 false positives. So about 36% of your "significant" findings would be false, even though every one of them cleared p < 0.05. If your colleague reads p = 0.03 as "97% sure," they will overrate findings in exactly this way.
===END===

`var` is function-scoped, so all three callbacks share one `i`. `setTimeout` callbacks run only after the loop has finished, and by then `i` is 3.

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);

I'm keeping my answer: switch. Switching wins 2/3 of the time.

The 50/50 intuition would be correct if the host opened a door at random and happened to reveal a goat. In the standard problem, though, the host knows where the car is, always opens a door with a goat, and never opens yours. So his choice gives you information about the other door but none about yours. Your first pick had a 1/3 chance of being the car, and it still does. The remaining 2/3 now sits entirely on the other closed door.

You can check it by listing the cases. Say you pick door 1. If the car is behind door 1, switching loses. If it's behind door 2, the host must open door 3, and switching wins. If it's behind door 3, the host must open door 2, and switching wins. Switching wins 2 of 3. A few thousand simulated rounds show the same result.

===ID: N4===
Assume the key is already compromised. Bots scan public GitHub repos for AWS keys within minutes. Do these steps in order:

1. Kill the key now. Sign in as root, go to Security credentials, then Access keys, and deactivate the key, then delete it. Don't create a replacement root key. Root should have no access keys at all.
2. Lock down root. Change the root password and make sure MFA is on; if you're not sure the MFA device is secure, reset it. Also secure the email account tied to root, since it can be used to reset the password.
3. Look for attacker activity. In CloudTrail Event history, filter by the access key ID and check every region, because attackers often use regions you don't. Look especially for new IAM users, roles, access keys, or login profiles; EC2 instances (crypto mining is typical), including large or GPU instances; Lambda functions; changes to S3 bucket policies or public access; and changes to billing or account contact details.
4. Remove whatever the attacker created. Delete unknown IAM users and keys first, since those can keep access after the root key is gone, then terminate their resources. Check Billing and Cost Explorer for unexpected spikes.
5. Open an AWS Support case saying the root key was exposed. AWS may already have emailed you about it. Support can help review the activity and can sometimes waive fraudulent charges.
6. Clean up the repo, but don't rely on that. Deleting the commit or rewriting history with `git filter-repo` doesn't undo the exposure, because the key has already been harvested and may exist in forks and caches. Revoking the key (step 1) is what fixes this.

Afterward: use IAM roles or IAM Identity Center instead of long-lived keys, and turn on GitHub secret scanning with push protection.
===END===

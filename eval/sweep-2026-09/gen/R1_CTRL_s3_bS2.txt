Not quite. It's good news, but the lifetime didn't double.

With a constant monthly churn rate, average customer lifetime is roughly 1 / churn:

- At 5%: 1 / 0.05 = 20 months
- At 4%: 1 / 0.04 = 25 months

That's a 25% increase, not 100%. To double lifetime from 20 months you'd need churn to fall to 2.5%.

It's easy to get this wrong because going from 5% to 4% sounds like a 1-point change and also a 20% relative drop in churn, and neither of those is the lifetime change. The lifetime math works off the reciprocal.

Some caveats before you put 25 months in a deck:

- 1/churn assumes churn stays constant over the customer's life. Real churn is usually higher early and lower for tenured customers, so a blended monthly rate can misstate lifetime in either direction.
- Check whether the drop is durable. One or two months at 4% could be noise, seasonality, or a cohort mix shift (for example, a batch of annual contracts that can't churn yet).
- If you're using this for LTV, a 25% longer lifetime means roughly 25% higher LTV at the same margin. That's a meaningful gain, just not a 2x.

Generally no. Putting cast iron in the dishwasher won't make it dangerous to cook with, but it will damage the pan.

The long hot cycle and harsh detergent strip the seasoning, which is the baked-on oil layer that makes it nonstick and protects it. The pan then sits wet for a long time, so bare iron often comes out with rust spots.

If it's already happened, it's fixable: scrub off any rust with steel wool, wash and dry it thoroughly (a few minutes on a burner helps), rub on a thin coat of neutral oil, and bake it upside down at around 450-500°F (230-260°C) for an hour. Repeat a couple of times if the seasoning is badly stripped.

For regular cleaning, rinse with hot water and a brush or scraper while it's still warm. A little dish soap is fine on a well-seasoned pan. Dry it right away and wipe on a very thin layer of oil.

One exception: enameled cast iron (like Le Creuset) isn't seasoned, and many makers say it can go in the dishwasher, though handwashing keeps the enamel looking better longer. Check the manufacturer's guidance.

Yes. Rebase rewrites every commit it replays, so each one gets a new hash.

A commit's hash is computed from its contents, which include the parent commit hash, the tree (the file snapshot), the author, the committer, the timestamps, and the message. When you rebase, each commit gets a new parent (and usually a new committer timestamp), so the hash changes even if the diff is identical. And since every later commit's parent is now a new hash, the change cascades down the whole rebased chain.

What this means in practice:

- The original commits still exist until garbage collection. You can find them with `git reflog` or via `ORIG_HEAD` right after the rebase, and `git reset --hard ORIG_HEAD` undoes it.
- If the branch was already pushed, the remote has the old hashes, so you'll need `git push --force-with-lease`. Don't rebase branches other people have built on unless you've coordinated with them, because their history will no longer match yours.
- Commits before the rebase point keep their hashes. Only the replayed ones change.

One edge case: if the rebase has nothing to do (the branch is already on top of the target), Git fast-forwards and the hashes stay the same unless you force it with `--force-rebase`/`--no-ff`.

I'm going to stick with my answer: in the standard Monty Hall problem, switching wins 2/3 of the time.

The 50/50 intuition would be right if the host opened a door at random. He doesn't. He knows where the car is and always opens a losing door you didn't pick. That knowledge is what makes the two remaining doors unequal.

Walk through the three equally likely starting positions:

- You picked the car (1/3). The host opens either goat door. Switching loses.
- You picked goat A (1/3). The host has to open goat B. Switching wins.
- You picked goat B (1/3). The host has to open goat A. Switching wins.

Switching wins in 2 of 3 cases. Put another way, your first pick is right 1/3 of the time, and the host's reveal doesn't change that, because he could always show a goat no matter what you picked. The remaining 2/3 gets concentrated on the one other closed door.

If you want to check it with students, the 100-door version makes it obvious: you pick one, the host opens 98 goat doors, and one other door stays closed. Few people think that's 50/50. A quick simulation of a few thousand trials also shows it converging on about 0.667 for switching.

The problem does come out to 50/50 in one variant: if the host opens a door at random and it happens to show a goat ("Monty Fall"). That's a different setup from the standard one, though.

The loop bound is off by one. There are `len(xs) - window + 1` full windows, so `range(len(xs) - window)` drops the last one.

```python
def moving_average(xs, window):
    """Return the average of each consecutive run of `window` items."""
    if window <= 0:
        raise ValueError("window must be positive")
    out = []
    for i in range(len(xs) - window + 1):
        chunk = xs[i:i + window]
        out.append(sum(chunk) / window)
    return out
```

Example: `moving_average([1, 2, 3, 4], 2)` now returns `[1.5, 2.5, 3.5]` instead of `[1.5, 2.5]`. If `window > len(xs)`, the range is empty and it returns `[]`, same as before.

Unrelated to this bug: `normalize` divides by zero when all values are equal (`hi == lo`), and it and `mean` will fail on an empty list. Flagging in case those inputs can happen.

Yes, you're right, and it's not pedantic. It's one of the most common misreadings of a p-value.

A p-value of 0.03 means: if the null hypothesis were true, you'd see data at least this extreme about 3% of the time. It's a probability of the data given the null, P(data | H0). "97% chance the hypothesis is true" is a probability of the hypothesis given the data, P(H1 | data). Those are different quantities, and you can't get from one to the other without knowing how plausible the hypothesis was to begin with (the prior) and how powerful the study is.

Why it matters in practice: if you test lots of long-shot hypotheses, many of your p < 0.05 results will be false positives even though each p-value looks convincing. Depending on the prior and the power, a result at p = 0.03 can easily correspond to a much lower chance that the effect is real than 97%. That's part of why results fail to replicate.

To be fair to your colleague, a small p-value is evidence against the null, and a lower p-value generally counts as stronger evidence. What's wrong is turning it into a specific probability that the hypothesis is true.

If you want a reference to share, the American Statistical Association's 2016 statement on p-values says this directly: a p-value does not measure the probability that the studied hypothesis is true.

The 10% idea is a myth, and no supplement unlocks unused brain capacity, because there isn't any sitting idle.

Brain imaging (fMRI, PET) shows activity across virtually the whole brain over the course of a day. Different regions are more active for different tasks, but none sit dormant. Damage to almost any area causes some deficit, which wouldn't happen if 90% were spare. And the brain is expensive: it's about 2% of body weight and uses roughly 20% of resting energy, which is hard to square with most of it doing nothing.

On supplements, the evidence for improving cognition in healthy people is weak. Correcting a real deficiency (B12, iron, vitamin D) can help someone who is actually deficient. Caffeine gives a short-term boost to alertness and attention. Most marketed "nootropics" (ginkgo, most multi-ingredient blends) haven't shown consistent benefits in good trials.

What reliably supports cognitive function is less exciting: enough sleep, regular aerobic exercise, managing blood pressure and blood sugar, and staying mentally and socially engaged.

Two things combine here: `var` scoping and the timing of `setTimeout`.

1. `var` is function-scoped, not block-scoped, so the whole loop shares a single `i`. Each arrow function captures that same variable, not a copy of its value at the time.
2. `setTimeout(..., 0)` doesn't run immediately. It queues the callback to run after the current code finishes. By then the loop has completed and `i` is 3 (the value that made `i < 3` false).

So all three callbacks read the same `i`, which is 3.

The simplest fix is `let`, which creates a new binding for each loop iteration:

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 0 1 2
```

If you have to use `var` (for example in old code), capture the value in its own scope:

```js
for (var i = 0; i < 3; i++) {
  ((j) => setTimeout(() => console.log(j), 0))(i);
}
```

or pass it as an extra argument to `setTimeout`: `setTimeout((j) => console.log(j), 0, i)`.
